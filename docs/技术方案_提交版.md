# 基于大语言模型与进化算法的昂贵优化求解器

## 一、选题背景和我的思路

这次的题目是把大语言模型（LLM）和进化算法（EA）结合起来去解昂贵优化问题。所谓昂贵优化，指的是目标函数评价一次的代价特别高——可能是一次几小时的仿真，也可能是一次要花钱的实验，所以总的评价次数被卡得很死。题目要求把最大评价次数限制在 300 次以内，单目标和多目标都是这个数。我选的是单目标，因为想先把一条路走通，多目标可以在这个基础上再扩展。

一开始我查了一些资料，发现现在 LLM 辅助 EA 大致分几类做法：有的直接把 LLM 当优化器用，把历史解和分数写进提示词让它给出更好的解（比如 OPRO、LMEA）；有的让 LLM 去设计算法或启发式，进化的对象是代码而不是解（FunSearch、EoH）；还有的把 LLM 当代理模型，用来预测或者比较解的好坏，从而省下真实评价。昂贵优化最缺的就是评价次数，所以我觉得第三条路——用 LLM 当代理去筛选候选解——和这个场景最搭。

不过纯粹用一个大模型当代理有个很现实的问题：大模型又慢又贵。如果每一代产生的几十个候选解都拿去问大模型，成本根本扛不住，这就和"省评价"的初衷矛盾了。想到这一点之后，我定了两个自己觉得有意思、而且现有文献里做得不多的切入点，作为这个求解器的核心。

第一个想法是**分层代理**，也就是粗筛加精判。进化算法每一代会生成很多候选，但真正值得花评价的只有少数几个。我用一个便宜的小模型先把所有候选粗粗打一遍分，扔掉明显差的，只留一小部分；再用贵一点、准一点的大模型对留下来的做精细排序，最后选出前几名去真实评价。这样一来，昂贵的大模型只在很少的候选上跑，绝大部分打分量都由小模型承担，总成本降下来了，而排序质量并没有损失太多——因为小模型虽然糙，但排除掉那些一眼就差的解是绰绰有余的。

第二个想法是**预算感知的调度**。我不想让 LLM 的调用变成一个固定动作（比如每三代调一次），而是让一个调度器根据当前搜索的状态来决定什么时候、以多大力度动用 LLM。它盯着三个信号：种群的多样性、最优值有没有陷入停滞、还剩多少预算。多样性掉得太低或者一直没进步，说明可能卡在局部最优了，这时候就叫 LLM 生成一些"跳出性"的新解注入进去；预算充足的时候每代多评价几个点、多攒点数据，预算紧张了就少评价、更依赖代理的判断。核心思想是把 LLM 当成一种应急手段，而不是常规操作。

## 二、问题定义

我用 BBOB 风格的三个标准测试函数来验证，分别是 Sphere、Rosenbrock 和 Rastrigin。选这三个是因为它们难度有梯度：Sphere 是光滑的碗状函数，最简单；Rosenbrock 有一条又窄又弯的山谷，属于病态但单峰；Rastrigin 有大量局部最优，是典型的多峰难题。这样既能看方法在简单问题上能不能收敛，也能看它在难问题上会不会崩。

维度取 10 维，目标是最小化，三个函数的全局最优值都是 0。有一个细节我特意处理了：把最优点做了随机平移，不让它落在原点这种"好看"的位置上。因为 LLM 见过很多优化问题，如果答案恰好在原点，它有可能是"猜"出来而不是真的搜出来的，那样结果就不可信了。平移之后每个随机种子对应的函数实例是固定的，保证不同方法比的是同一张卷子。

昂贵场景是靠限制评价次数模拟出来的——函数本身算得并不慢，但我把最大真实评价次数硬性锁在 300，超了就停。这一点是整个实现里最需要守住的约束。

## 三、方法与实现

整个求解器是一个受预算约束的进化主循环。开始时我用拉丁超立方在搜索空间里撒 20 个点，做真实评价，作为初始数据。之后进入循环，每一代做这么几件事：先从历史里挑出最好的一批点当作喂给 LLM 的上下文，同时用一个保持多样性的方式选出当前种群；然后调度器根据前面说的三个信号给出决策；接着进化算子（我用了 DE 变异、BLX 交叉和高斯变异的组合）在种群基础上生成一个 50 个候选的池子，如果调度器判断需要跳出，就再让 LLM 补充几个探索点进来；最后两阶段漏斗从这 50 个里筛出少数几个，只对它们做真实评价，更新历史和当前最优。如此往复，直到 300 次预算用完。

代码结构上我按职责把功能拆开，整体是这样组织的：

```
├── src/                  核心算法
│   ├── problems.py       测试函数（Sphere / Rosenbrock / Rastrigin，带随机平移）
│   ├── evaluator.py      评价器：计数、强制 300 次上限、记录收敛曲线
│   ├── ea.py             进化算子：拉丁超立方、DE/BLX/高斯变异、多样性保持选择
│   ├── llm_client.py     LLM 客户端：抽象接口 + 真实 API(DeepSeek) + 离线模拟
│   ├── surrogate.py      创新一：两阶段粗筛→精判漏斗
│   ├── scheduler.py      创新二：预算感知调度器
│   ├── solver.py         主循环：把上面这些串起来
│   └── baselines.py      对照方法：随机搜索、标准 DE
├── experiments/
│   └── run_experiment.py 实验入口：跑各方法、存 CSV、画收敛图
├── tests/
│   └── test_core.py      单元测试：预算上限、漏斗、调度器
├── requirements.txt      依赖
└── docs/                 说明文档
```

拆分的原则是让每个文件只管一件事，互相之间靠明确的接口调用。最关键的是 `evaluator.py` 里的评价器，它是唯一能触碰真实目标函数的地方，每评价一次就计数一次，到 300 立刻拒绝再算——所有方法（包括随机和 DE 两个对照）都必须经过它，这样才能保证大家是在同一个预算下比。`solver.py` 是总调度，它每一代先问 `scheduler.py` 拿决策，再让 `ea.py` 生成候选池，交给 `surrogate.py` 的漏斗去筛，最后把选中的少数解送回评价器。两个创新点分别独立在 `surrogate.py` 和 `scheduler.py` 里，我特意把调度器写成不碰 LLM、也不碰评价的纯逻辑，这样单元测试里可以直接构造各种状态去验证它的判断，不用真的跑一遍完整流程。

另外，`solver.py` 里还留了几个开关，用来做消融和对比：`use_funnel` 关掉就是"AI 只当调度器"，`use_scheduler` 关掉就是"只用两阶段漏斗"，`single_tier` 打开就是"只用大模型不做粗筛"。这样四种配置——完全不用 AI、只用调度、只用大小模型、两个都用——都能从同一套代码里跑出来，改的只是参数，算法主体没有重复。

这里有个工程上的决定我觉得值得说一下。求解器并不直接跟某个具体的 LLM 打交道，而是依赖一个抽象的客户端接口，下面有两个实现。一个是真实的 API 客户端，兼容 OpenAI 格式的接口，小模型和大模型就是同一个端点上的两个模型名，我实际接的是 DeepSeek。另一个是离线的模拟客户端，它用一个内部的小回归器拟合上下文里的数据，再按档位加不同大小的噪声，小模型噪声大、大模型噪声小，以此模拟"糙但快"和"准但贵"这两档的差别。之所以做这个模拟版，是因为真实大模型（尤其是推理型的）调用一次很慢，跑完整的多方法、多种子、300 预算实验要花几个小时还要花钱，根本不现实；而算法逻辑在两种模式下是完全一样的，用模拟版跑主实验、用真实 API 做小规模验证，是处理这类问题比较务实的办法。真实调用时我也加了容错，模型要是返回了格式不对的东西，就退回到最近邻估计，不会让整个程序崩掉。

## 四、实验结果与分析

主实验在离线模拟模式下跑，每个配置用 5 个随机种子取平均，预算 300、维度 10。除了完整方法，我还做了消融：把两阶段漏斗换成只用大模型（验证分层到底省不省），以及关掉调度器（验证调度有没有用）。对照组是随机搜索和标准 DE。

最终最优值（越小越好）大致是这样：

| 问题 | 随机搜索 | 标准 DE | 完整方法 | 只用大模型 | 无调度 |
|---|---|---|---|---|---|
| Sphere | 30.6 | 9.37 | 0.34 | 0.39 | 0.52 |
| Rosenbrock | 20731 | 3423 | 71.5 | 474 | 113.6 |
| Rastrigin | 105.4 | 80.4 | 34.0 | 33.0 | 43.6 |

从这张表能看出几件事。首先完整方法在三个函数上都明显好于随机搜索和标准 DE，Rosenbrock 上尤其夸张，从 DE 的三千多降到了七十几。这说明在评价预算极少的情况下，让代理帮忙挑解、把评价花在刀刃上，确实比多而盲目地评价更划算。

关于第一个创新，光看质量还不够，得看成本。我统计了每次运行大模型的打分次数：完整方法里大模型只打了大约 970 次分，而"只用大模型"那一版打了 5292 次，差不多是 5 倍多。也就是说两阶段漏斗把最贵的那部分调用砍掉了五分之四，与此同时解的质量在 Sphere 和 Rosenbrock 上还更好、在 Rastrigin 上基本持平。如果按大模型比小模型贵二十倍来估算，总的 LLM 成本大概能省到四分之一左右。这个结果和我一开始的判断是一致的——小模型足够胜任粗筛，把大模型的算力留给真正需要精细判断的少数候选。

第二个创新的效果也能从消融里看出来。完整方法在三个函数上都比"无调度"版本好，说明根据预算动态调整评价数量、在卡住的时候注入跳出解，是有稳定收益的。

当然也有讲不通或者说效果一般的地方，我不打算回避。Rastrigin 上完整方法和"只用大模型"几乎打平，两阶段的排序优势在这种强多峰问题上被问题本身的难度盖过去了，这时候更需要的是更强的探索机制而不是更精细的筛选。另外这些主结果是基于模拟 LLM 得到的，真实大模型的排序能力、幻觉率和延迟都会影响结论，所以我另外用 DeepSeek-V4 的真实接口做了一次小规模验证，跑通了整条流水线，确认在真实模型下也能正常工作。最后就是规模，三个函数、10 维、300 次评价只能算初步验证，要下更硬的结论还得扩到更多函数、更多维度，并且做统计显著性检验；LLM 调用本身的时间和金钱成本也还没有算进统一的预算模型里，这些都是可以接着做的方向。

## 五、小结

总的来看，我用"分层代理"和"预算感知调度"这两个不算复杂的机制，在 300 次评价的昂贵场景下既把解的质量提上去了，又把昂贵大模型的用量压了下来，两个点都通过消融实验得到了验证。虽然离一个成熟的方法还差得远，但作为对"不同规模 LLM 分层做代理"和"LLM 调用时机决策"这两个方向的探索，我觉得这个小求解器把想法说清楚、也验证到位了。
